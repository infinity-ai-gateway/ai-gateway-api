# Rainway AI Gateway - 总体设计文档

## 1. 概述

### 1.1 定位

`ai-gateway-api` 是 AI 网关的**控制面核心组件**，负责对外暴露管理面 OpenAPI 与数据面 InnerAPI，完成策略/配置的创建、存储、版本控制和下发。它向上为 Dashboard 和自动化脚本提供管理接口，向下为 BFE 数据面和 Conf Agent 生成可消费的配置快照。

本文档用于帮助读者和大模型快速建立对 `ai-gateway-api` 系统设计的整体认知。关于数据库、存储层、模型层、接口层的详细设计，请分别阅读同目录下的：

- 《数据库设计文档.md》
- 《存储层设计文档.md》
- 《模型层设计文档.md》
- 《接口层设计文档.md》

### 1.2 项目上下文

AI 网关整体由以下核心组件构成：

| 组件 | 角色 | 说明 |
|------|------|------|
| **AI Gateway API** | 控制面 | 即本项目，负责配置管理和配置下发 |
| **Dashboard** | 管理控制台 | Web UI，调用 OpenAPI 完成可视化操作 |
| **BFE** | 数据面 | 流量转发与访问控制 |
| **EPP** | 数据面 | LLM 推理调度器（基于 llm-d），消费 epp_data 配置接管 EPP 模式 cluster 的后端选择 |
| **Conf Agent** | 配置代理 | 从 InnerAPI 拉取最新配置并触发 BFE 热加载 |
| **Service Controller** | 服务发现 | 发现并同步 Kubernetes 后端服务 |

### 1.3 功能范围

`ai-gateway-api` 当前代码实现的功能范围如下：

- **API-Key 管理**：创建、查询、更新、删除 API-Key；支持配额计划、限流策略和路由规则；创建时支持传入外部 `key`，列表/详情中 `quota_plan` 包含 `balance`。
- **Entity 管理**：创建、查询、更新、删除 Entity，支持层级结构、配额/限流和路由规则。
- **Entity-Type 管理**：创建、查询、更新、删除 Entity 类型定义。
- **配额计划管理**：查询和重置配额余额；`QuotaPlan` 支持 `unit = "total_token"` 与 `unit = "RMB"`。
- **限流策略管理**：TPM、RPM、并发限制配置。
- **路由规则管理**：API-Key/Entity 级路由规则、Global 路由表、路由表列表查询；AI 路由规则不再通过 `/ai-route-rules` 独立暴露。
- **AI 网关实例池管理（`/alb-pool`）**：获取和更新默认 AI 网关实例池。
- **认证授权管理（`/auth`）**：用户、Session Key、Token；Token Scope 仅保留 `System`/`Support`，移除产品线授权。
- **证书管理（`/certificates`）**：证书创建、列表、详情、设置默认证书、删除；创建/更新时仅需上传证书与密钥内容，`expired_date` 由服务端从证书中解析，不再要求上传文件名。
- **Provider 管理（`/providers`）**：创建、查询、更新、删除 Provider；支持 `model_endpoint`、`models`、`keys`、`instance_pool`、`model_protocols` 等字段，集中管理下游模型提供方的接入能力；提供 `/providers/tools/discover-models` 无状态工具接口触发模型发现，返回模型名列表。
- **集群管理（`/clusters`）**：集群一键创建、查询、更新、删除；`llm_config` 只保留转发策略（含 `models`、`model_mappings`、`keys` Key 引用与权重、`key_policy`、`key_affinity`、`provider`、`match_prefix`/`strip_prefix` 等），后端实例池、Key 明文、模型端点等能力通过 `llm_config.provider` 引用 Provider 获取；集群就绪状态、子集群、调度矩阵等内部概念不再对外暴露；`llm_config.provider` 用于 InnerAPI 自动填充 `AIConf.ModelTable`。
- **模型定价管理（`/model-prices`）**：导入 `model-list.yaml`、单条 CRUD、分页查询、查询所有 Provider 名称列表（`GET /model-prices/actions/get-providers`）；`provider` 字段仅作为价格归集标识，不强制引用 `/providers` 中已存在的 Provider，为 RMB 配额与 BFE 成本核算提供统一模型定价数据源。
- **EPP 调度管理（`/epp-pool`、`/epp-assignments`、`/clusters`）**：cluster 均衡模式与调度配置（`balance_mode`/`epp_config`）、EPP 实例池单例管理（`/epp-pool` 全量替换）、cluster→EPP 实例组自动分配（贪心 + 字典序 tie-break，含 30s 周期对账 reconciler）与分配查询/手工覆写（`/epp-assignments`）、epp_data 统一下发（`ConfigTopicEppData`：epp_config 编译产物 + assignment 全量视图，单 topic 两段合并）。
- **操作日志管理（`/operation-logs`）**：记录控制面配置变更操作，覆盖 cluster、route、domain、certificate、quota_plan、rate_limit_policy、model_price、user、token、entity、api_key、provider 等域；支持按操作人、资源类型、动作、时间范围分页查询；对 api-key token、密码、私钥、证书等敏感字段统一脱敏；采用异步批量写入降低主请求延迟，失败操作同样记录。

- **配置导出（InnerAPI）**：向 BFE/Conf Agent 导出 TLS/Server/路由、GSLB、证书、附加文件、API-Key、请求体处理、限流策略、AI 路由等配置；`server_data_conf` 中 `ClusterConf.Config.<cluster_name>.AIConf` 新增 `Provider`、`ModelTable`、`MatchPrefix`、`StripPrefix` 与 `ModelProtocols`；EPP 模式 cluster 导出 `GslbBasic.BalanceMode=EPP` 与有序 `EPPAddr [主, 备]`（无有效分配时降级为该 cluster `BalanceMode=WRR` + error 日志，不阻塞整份下发）；向 EPP 实例导出 `epp_data`（`/configs/epp_data/config`）。

## 2. 架构总览

### 2.1 分层架构

系统采用经典的三层架构：

```
┌─────────────────────────────────────────────────────────────┐
│ 接口层 (endpoints) │
│ OpenAPI v1 (/open-api/v1) · InnerAPI v1 (/inner-api/v1) │
├─────────────────────────────────────────────────────────────┤
│ 模型层 (model) │
│ 业务逻辑 · 事务编排 · 参数校验 · 级联操作 │
├─────────────────────────────────────────────────────────────┤
│ 存储层 (storage/rdb) │
│ DAO · Storage 实现 · 关系型数据库读写 │
└─────────────────────────────────────────────────────────────┘
```

| 层次 | 主要职责 | 关键包 |
|------|----------|--------|
| **接口层** | 处理 HTTP 请求、参数绑定与校验、权限校验、调用模型层、返回统一响应 | `endpoints/openapi_v1`、`endpoints/innerapi_v1`、`endpoints/middleware` |
| **模型层** | 封装业务逻辑、事务管理、调用存储层接口；不直接依赖底层数据库 | `model/*` |
| **存储层** | 负责关系型数据库的读写；向上暴露接口，由模型层通过事务抽象调用 | `storage/rdb/*` |

### 2.2 组件交互关系

```
                HTTP Request
                     │
        ┌────────────┴────────────┐
        ▼ ▼
  /open-api/v1 /inner-api/v1
  (管理面 OpenAPI) (数据面 InnerAPI)
        │ │
        └────────────┬────────────┘
                     ▼
           endpoints/middleware
         (Recovery / Logger / CORS /
          Product Probe / User Probe)
                     │
                     ▼
            endpoints/xreq.Endpoint
                     │
                     ▼
              model/* Manager
                     │
                     ▼
         model/itxn.TxnStorager
                     │
        ┌────────────┼────────────┐
        ▼ ▼ ▼
   storage/rdb storage/rdb storage/rdb
   /cluster_conf /quota /route_conf
        │ │ │
        └────────────┼────────────┘
                     ▼
              storage/rdb/internal/dao
                     │
                     ▼
                MySQL / SQLite
```

- **接口层**通过 `stateful/container` 中注册的全局单例 Manager 调用模型层，不直接访问存储层。
- **模型层**只依赖同包或 `model/shared` 中定义的 `XxxStorager` 接口，以及 `model/itxn.TxnStorager` 事务抽象。
- **存储层**实现上述接口，内部通过 `storage/rdb/internal/dao` 操作具体的数据库表。

### 2.3 配置与运行时

- **配置加载**：`main.go` 调用 `stateful.LoadConfig` 加载 TOML 配置文件（默认 `conf/ai_gateway_api.toml`）。
- **数据库初始化**：`Config.InitDB()` 根据配置创建 `sql.DB` 连接池，支持 MySQL 与 SQLite。
- **依赖注入初始化**：`stateful/container/rdb.Init()` 按依赖顺序实例化所有 Storager 与 Manager，并注入 `stateful/container` 全局变量。
- **HTTP 服务启动**：`endpoints.RegisterRouters` 注册 OpenAPI 与 InnerAPI 路由，最终通过 `negroni` + `graceful` 启动 HTTP 服务。

## 4. 数据库设计（概要）

`ai-gateway-api` 当前代码实现中共使用 31 张关系型数据表，按业务模块划分如下：

| 模块 | 表名 |
|------|------|
| 基础配置 | `bfe_clusters`、`products`、`domains`、`users`、`user_products`、`config_versions` |
| Provider | `providers` |
| 集群与实例池 | `clusters`、`sub_clusters`、`pools`、`lb_matrices`、`epp_instances`、`epp_assignments` |
| 路由规则 | `route_basic_rules`、`route_advance_rules`、`route_default_rules`、`route_cases`、`ai_route_rules`、`route_rules` |
| 证书与附加文件 | `certificates`、`extra_files` |
| API Key / Entity / 配额 / 限流 | `api_keys`、`api_key_id_seq`、`api_key_tokens`、`entity_types`、`entities`、`entity_id_seq`、`quota_plans`、`rate_limit_policies` |
| 模型定价 | `model_prices` |
| 操作日志 | `operation_logs` |

### 4.1 关键约定

- 底层驱动为标准库 `database/sql`，SQL 构建器使用 `github.com/didi/gendry`。
- 支持 MySQL 5.7+ 与 SQLite。
- 所有表均包含 `created_at` 与 `updated_at` 字段。
- 数据库 DDL **未声明物理 FOREIGN KEY 外键约束**，表间关系由应用层代码维护。
- AI 相关表使用 `utf8mb4`；历史表主要使用 `utf8`。

### 4.2 核心表简介

| 表 | 作用 |
|----|------|
| `api_keys` | API-Key 主表，通过 `quota_plan_id`、`rate_limit_policy_id`、`route_rules_id`、`entity_id` 关联配额、限流、路由规则与 Entity |
| `api_key_id_seq` | API-Key ID 序号分配表，按 `product_name` 原子分配 `api-key-{seq}` 序号，分配即消耗、删除后不回退 |
| `entities` | Entity 实体表，支持层级结构（`parent_id`）与模型白/黑名单 |
| `entity_id_seq` | Entity ID 序号分配表，原子分配 `entity-{seq}` 序号，分配即消耗、删除后旧 ID 不复用 |
| `entity_types` | Entity 类型定义表，定义类型名、层级级别 |
| `quota_plans` | 配额计划表，记录是否无限配额、配额总量、重置周期、上次重置时间等 |
| `rate_limit_policies` | 限流策略表，记录 TPM/RPM 配置与最大并发数 |
| `route_rules` | API-Key/Entity/Global 级 AI 路由规则表 |
| `ai_route_rules` | 历史 AI 路由规则明细表，OpenAPI 不再通过 `/ai-route-rules` 暴露 |
| `certificates` | TLS 证书表 |
| `extra_files` | 附加文件表，用于 InnerAPI 导出 |
| `clusters` | AI 集群配置表；除转发策略（`llm_config`）外，新增 `balance_mode`（均衡模式，唯一判定来源）与 `epp_config`（EPP 调度配置简化用户形态）两列 |
| `epp_instances` | EPP 实例池表，一行一个 EPP 实例（id、host、port、group_name），`(host, port)` 池内唯一，无 status/heartbeat |
| `epp_assignments` | cluster→EPP 实例组分配表（cluster 唯一键），只存主（`primary_instance_id`），standby 读时展开 |

更多表结构、字段含义、索引设计和 DDL 详见《数据库设计文档.md》。

## 5. 存储层设计（概要）

存储层位于 `storage/rdb`，采用 **DAO + Storage** 两层结构。

### 5.1 架构角色

| 组件 | 职责 |
|------|------|
| `storage/rdb/internal/dao` | 按表提供 `T<Table>One/List/Create/Update/Delete` 函数，直接操作数据库 |
| `storage/rdb/*` | 实现 `model/*` 中定义的 `XxxStorager` 接口，完成 DAO 结果与业务模型的转换 |
| `storage/rdb/txn` | 实现 `model/itxn.TxnStorager` 事务抽象 |

### 5.2 DAO 通用模式

每个 DAO 文件遵循统一模板：

1. 表名常量：`const t<Table>TableName = "<table_name>"`
2. 结果结构体：`T<Table>`，字段使用 `db:"column_name"` 标签
3. 参数结构体：`T<Table>Param`，字段多为指针类型，包含 `_orderby`、`_limit` 控制字段
4. CRUD 函数：`T<Table>One`、`T<Table>List`、`T<Table>Create`、`T<Table>Update`、`T<Table>Delete`

### 5.3 Storage 实现组织

| 存储包 | 对应模型包 | 覆盖表 |
|--------|------------|--------|
| `storage/rdb/auth` | `model/iauth` | `users`、`user_products` |
| `storage/rdb/basic` | `model/ibasic` | `bfe_clusters`、`products`、`extra_files` |
| `storage/rdb/api_key` | `model/api_key` | `api_keys`、`api_key_tokens` |
| `storage/rdb/cluster_conf` | `model/icluster_conf` | `clusters`、`sub_clusters`、`pools`、`lb_matrices` |
| `storage/rdb/epp_pool` | `model/epp_pool` | `epp_instances`、`epp_assignments` |
| `storage/rdb/entity` | `model/entity` | `entity_types`、`entities` |
| `storage/rdb/protocol` | `model/iprotocol` | `certificates` |
| `storage/rdb/quota` | `model/quota` | `quota_plans` |
| `storage/rdb/rate_limit_policy` | `model/rate_limit_policy` | `rate_limit_policies` |
| `storage/rdb/route_conf` | `model/iroute_conf` | `domains`、`route_basic_rules`、`route_advance_rules`、`route_default_rules`、`route_cases` |
| `storage/rdb/route_rules` | `model/shared`、`model/route_rules` | `route_rules` |
| `storage/rdb/ai_route` | `model/iai_route` | `ai_route_rules` |
| `storage/rdb/version_control` | `model/iversion_control` | `config_versions` |

更多 DAO 清单、Storage 接口定义、事务实现和典型示例详见《存储层设计文档.md》。

## 6. 模型层设计（概要）

模型层位于 `model/`，采用 **Manager + Storager 接口** 的分层模式。

### 6.1 核心抽象

| 类型 | 说明 |
|------|------|
| `XxxParam` | 创建/更新入参，字段多为指针类型以区分“未传”与“零值” |
| `XxxFilter` | 查询条件，包含分页字段 `Page` / `PageSize` |
| `XxxStorager` | 定义持久化操作契约，由 `storage/rdb/` 各子包实现 |
| `XxxManager` | 业务逻辑实现，聚合 `itxn.TxnStorager` 与其它 `Storager` |

### 6.2 模型包职责

| 模型包 | 主要职责 |
|--------|----------|
| `model/api_key` | API-Key 业务逻辑、级联删除、实时配额查询、mod-api-key 导出数据源 |
| `model/entity` | Entity / Entity-Type 业务逻辑、层级校验、级联删除、Entity 相关导出数据源 |
| `model/iauth` | 用户/Token 认证、产品线授权、Feature-Action 权限定义 |
| `model/ibasic` | Product、BFECluster、ExtraFile 业务逻辑 |
| `model/icluster_conf` | Cluster、SubCluster、Pool 业务逻辑；`LLMConfig` 只保留转发策略，通过 `provider` 引用 Provider 获取后端能力；导出 `AIConf` 时按 name join Provider 的 key 明文与 Cluster 的 key 权重，填充 `Provider`、`ModelTable`、`MatchPrefix`、`StripPrefix` 与 `ModelProtocols`；`balance_mode`/`epp_config` 字段处理与 EPPAddr 分配驱动生成 |
| `model/epp_pool` | EPP 实例池读写（`/epp-pool` 单例池全量替换）、分配器（贪心 + 字典序 tie-break，含 30s 周期 reconciler）、epp_data generator（`ConfigTopicEppData`：epp_config 编译产物 + assignment 全量视图）、`epp_config` 简化用户形态 → `EndpointPickerConfig` 确定性编译 |
| `model/iprovider` | Provider 业务逻辑：CRUD、模型发现、被 cluster 引用检查 |
| `model/imodel_price` | `ModelPrice` 模型定价管理：`model-list.yaml` 导入、单条 CRUD、分页查询、按 provider 查询、查询所有 price provider 名称；`provider` 不强制引用已存在的 Provider |
| `model/iroute_conf` | 基础/高级路由规则、Domain 业务逻辑 |
| `model/iai_route` | AI 路由规则模型与校验 |
| `model/iprotocol` | TLS 证书模型与业务逻辑 |
| `model/imods` | mod-api-key、mod-body-process、AI 路由导出配置组装 |
| `model/ioperlog` | 操作日志管理：定义 `OperationLogEntry`/`OperationLogFilter`，提供 `OperationLogManager` 异步批量写入、脱敏工具函数与查询能力 |
| `model/quota` | QuotaPlan、BalanceSync、QuotaResetScheduler；`QuotaPlan` 支持 `unit=RMB`，`quota` 扩展为 `float64` / `DECIMAL(18,8)`；`last_reset_at` 保存在 `quota_plans` 表；周期重置通过 Redis 分布式锁互斥，并采用原子 `SET` + `last_reset_at` 条件更新实现幂等；`quota_balances` 表已删除，OpenAPI 余额直接读 Redis |
| `model/rate_limit_policy` | RateLimitPolicy 业务逻辑、层级收集与导出 |
| `model/quotacache` | API-Key / Entity 实时配额缓存抽象，封装 Redis `GetInt64` / `IncrBy` / Lua `SET` 操作，并提供基于 Redis Lua 的 `DistributedLock` 实现，供 `model/quota`、`model/api_key`、`model/entity` 调用 |
| `model/shared` | 跨包共享类型与接口（含 `RouteRulesStorager`） |
| `model/route_rules` | `RouteRulesManager`：Global/Entity/API-Key 路由规则业务逻辑 |
| `model/itxn` | 事务抽象接口 `TxnStorager` |
| `model/iversion_control` | 配置版本控制与增量导出 |

### 6.3 事务管理

```go
// model/itxn/txn.go
type TxnStorager interface {
    AtomExecute(ctx context.Context, do func(context.Context) error) error
}
```

`storage/rdb/txn` 提供基于 `database/sql` 的实现；Manager 通过 `container.TxnStoragerSingleton` 编排跨多个 Storager 的原子操作。

### 6.4 版本控制

`model/iversion_control` 为配置变更提供统一的版本号管理，InnerAPI 导出接口通过 `version` 参数实现增量同步：当请求版本与当前版本一致时返回 `Data: nil`。

更多模型结构、接口定义、Manager 初始化、典型业务流程详见《模型层设计文档.md》。

## 7. 接口层设计（概要）

接口层位于 `endpoints/`，统一使用 `xreq.Endpoint` 抽象：

```go
type Endpoint struct {
    Path string
    Method string
    Handler Handler
    Authorizer func(*http.Request) error
    RegisterHandler func(*mux.Router) *mux.Route
}
```

### 7.1 两大接口族

| 接口族 | 前缀 | 用途 | 中间件 |
|--------|------|------|--------|
| **OpenAPI v1** | `/open-api/v1` | 管理面接口，供 Dashboard/管理员使用 | `McProductProbe` + `McUserProbe` |
| **InnerAPI v1** | `/inner-api/v1` | 数据面导出接口，供 BFE/Conf Agent 拉取配置 | `McUserProbe` |

### 7.2 路由注册

- 根路由在 `endpoints/router.go` 中注册：全局 Recovery、Logger、CORS，静态文件服务。
- OpenAPI 路由在 `endpoints/openapi_v1/endpoints.go` 中合并各子包 Endpoint 切片注册。
- InnerAPI 路由在 `endpoints/innerapi_v1/endpoints.go` 中统一注册导出接口。

### 8.2 初始化顺序

`stateful/container/rdb/components.go:Init()` 按以下顺序完成初始化：

1. **事务与基础存储**：`TxnStoragerSingleton`、`VersionControlStoragerSingleton`、`RouteRuleStoragerSingleton`、各类基础/集群/认证存储，以及 `OperationLogStorager`。
2. **操作日志 Manager**：创建 `OperationLogManager`，设置请求上下文提取器（注入 `log_id`、请求路径、客户端 IP、User-Agent 等），并作为全局单例供后续各业务 Manager 注入。
3. **基础 Manager**：`ExtraFileManager`、`VersionControlManager`、`BFEClusterManager`、`CertificateManager`、`ProductManager`、`AIRouteRuleManager`、`RouteRuleManager` 等。
4. **集群相关 Manager**：`ClusterManager`、`SubClusterManager`、`DomainManager`、`PoolManager`。
5. **认证授权 Manager**：`AuthenticateManager`、`AuthorizeManager`。
6. **Entity / RateLimit / Quota 相关存储与 Manager**：在 `model/entity`、`model/rate_limit_policy`、`model/quota` 中分别初始化 EntityType、Entity、RateLimitPolicy、QuotaPlan、RouteRules 及其 Manager。
7. **模块导出 Manager**：`APIKeyRuleManager`、`ModBodyProcessManager`、`AIRouteExporter`。
8. **API-Key Manager**：注入 Quota/RateLimit/Entity 适配器，实现 `model/api_key` 与配额/限流体系的打通。
9. **周期重置**：`BalanceSyncManager`、`QuotaResetScheduler`，并启动调度器；`QuotaResetScheduler` 注入 Redis 分布式锁，保证多实例下同一时刻只有一个实例执行重置；`BalanceSyncManager` 只执行 `ResetExpiredBalances`，不再执行 `SyncAllBalances`。
10. **Global 路由表默认记录**：调用 `RouteRulesManager.EnsureGlobalRouteRules` 确保 `route_rules` 表中存在 `type=global, owner=global` 的默认记录；若已存在则跳过。

### 8.3 适配器模式

API-Key、Entity、RateLimitPolicy 已拆分为独立的 `model/api_key`、`model/entity`、`model/rate_limit_policy` 包，而 QuotaPlan 仍保留在 `model/quota`。代码中通过**适配器**（如 `quota.NewQuotaPlanStoragerAdapter`、`quota.NewEntityStoragerAdapter`、`quota.NewRateLimitPolicyStoragerAdapter`）将这些包中的 Storager 接口转换为 `model/shared` 中定义的通用接口，供 `APIKeyManager` / `EntityManager` 统一调用，实现跨包复用。其中 `quota.NewEntityStoragerAdapter` 接收 `entity.EntityStorager`，`quota.NewRateLimitPolicyStoragerAdapter` 接收 `rate_limit_policy.RateLimitPolicyStorager`。

## 10. 设计原则与约定

1. **分层解耦**：接口层只依赖模型层 Manager；模型层只依赖 Storager 接口和事务抽象；存储层只负责数据库读写。
2. **接口导向**：模型层通过 `XxxStorager` 接口定义持久化契约，便于未来替换存储实现。
3. **统一 Endpoint 抽象**：所有 HTTP 接口使用 `xreq.Endpoint` 描述，统一注册、鉴权和中间件处理。
4. **子包自治**：每个业务子包独立维护自己的 Endpoint、Action、Manager、Storager；顶层 `endpoints.go` 仅做合并。
5. **全局容器**：Manager 与 Storager 作为全局单例存在 `stateful/container`，通过 `rdb.Init()` 完成一次性初始化。
6. **版本控制**：配置变更统一由 `iversion_control` 管理版本，支持 InnerAPI 增量导出。
7. **无物理外键**：表间关系由应用层维护，DDL 不声明 FOREIGN KEY，便于分库分表与灵活变更。
8. **事务编排**：跨表/跨 Storager 的业务操作通过 `TxnStorager.AtomExecute` 保证原子性。
