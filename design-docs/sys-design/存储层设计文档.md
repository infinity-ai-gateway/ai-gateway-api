# 存储层设计（storage/rdb）

## 1. 概述

`ai-gateway-api` 的存储层位于 `storage/rdb`，采用**三层架构**中的最底层：

- **接口层**（`endpoints/openapi_v1`）：处理 HTTP 请求、参数校验，调用模型层。
- **模型层**（`model/*`）：处理业务逻辑、事务管理，调用存储层接口。
- **存储层**（`storage/rdb`）：负责关系型数据库的读写，采用 **DAO + Storage** 两层结构。

存储层向上暴露一组接口（定义在 `model/*` 各子包中），由模型层的 `Manager` 通过事务抽象 `model/itxn.TxnStorager` 调用；向下通过 `storage/rdb/internal/dao` 中的 DAO 函数操作具体的数据库表。

### 2.2 DAO 通用设计模式

每个 DAO 文件遵循统一的代码模板：

1. **表名常量**：`const t<Table>TableName = "<table_name>"`
2. **结果结构体**：`T<Table>`，字段使用 `db:"column_name"` 标签，与表字段一一对应。
3. **参数结构体**：`T<Table>Param`，字段均为指针类型，同样使用 `db:"column_name"` 标签；同时包含两个控制字段：
   - `OrderBy *string `db:"_orderby"`` — 排序
   - `Limit []uint `db:"_limit"`` — 分页（部分表支持）
4. **CRUD 函数**：
   - `T<Table>One(dbCtx, where)` — 查询单条，不存在时返回 `(nil, nil)`
   - `T<Table>List(dbCtx, where)` — 查询多条，不存在时返回 `(nil, nil)`
   - `T<Table>Create(dbCtx, data...)` — 单条/批量插入，自动填充 `CreatedAt`
   - `T<Table>Update(dbCtx, val, where)` — 按条件更新
   - `T<Table>Delete(dbCtx, where)` — 按条件删除

底层统一使用 `storage/rdb/internal/dao/internal` 包中的 `QueryOne`、`QueryList`、`Create`、`Update`、`Delete`，基于 `github.com/didi/gendry` 构建 SQL 并扫描结果。

### 3.2 Storage 通用设计模式

每个 Storage 实现遵循以下模式：

1. **依赖注入**：通过构造函数接收 `lib.DBContextFactory`，用于从 `context.Context` 获取 `lib.DBContexter`。
2. **接口断言**：使用 `var _ <Interface> = &<Storage>{}` 确保实现对应 model 层接口。
3. **类型转换**：在 model 参数/过滤条件与 DAO 参数/结果之间做转换。
4. **JSON 序列化**：复杂结构通过 `encoding/json` 序列化为字符串后存入数据库。
5. **时间戳处理**：使用 `lib.PTimeNow()` 等工具函数填充 `CreatedAt` / `UpdatedAt`。

示例：

```go
type EntityTypeStorager struct {
    dbCtxFactory lib.DBContextFactory
}

func NewEntityTypeStorager(dbCtxFactory lib.DBContextFactory) *EntityTypeStorager {
    return &EntityTypeStorager{dbCtxFactory: dbCtxFactory}
}

var _ entity.EntityTypeStorager = &EntityTypeStorager{}

func (s *EntityTypeStorager) CreateEntityType(
    ctx context.Context,
    param *entity.EntityTypeParam,
) (int64, error) {
    dbCtx, err := s.dbCtxFactory(ctx)
    if err != nil {
        return 0, err
    }

    data := &dao.TEntityTypeParam{
        TypeName: param.TypeName,
        Description: param.Description,
        Level: param.Level,
        CreatedAt: lib.PTimeNow(),
    }

    return dao.TEntityTypeCreate(dbCtx, data)
}
```

```go
func rateLimitPolicyDataToParam(param *rate_limit_policy.RateLimitPolicyParam) *dao.TRateLimitPolicyParam {
    data := &dao.TRateLimitPolicyParam{
        Enabled: param.Enabled,
        MaxConcurrency: param.MaxConcurrency,
    }

    if len(param.TpmConfigs) > 0 {
        tpmConfigsJSON, _ := json.Marshal(param.TpmConfigs)
        data.TpmConfigs = lib.PString(string(tpmConfigsJSON))
    } else {
        data.TpmConfigs = lib.PString("[]")
    }

    if len(param.RpmConfigs) > 0 {
        rpmConfigsJSON, _ := json.Marshal(param.RpmConfigs)
        data.RpmConfigs = lib.PString(string(rpmConfigsJSON))
    } else {
        data.RpmConfigs = lib.PString("[]")
    }

    return data
}

```

#### 3.3.11 ioperlog 域

实现文件位于 `storage/rdb/ioperlog/`，对应接口定义在 `model/ioperlog`。

| 文件 | Storage 结构 | 构造函数 | 实现接口 | 主要方法 |
|------|--------------|----------|----------|----------|
| `operation_log.go` | `OperationLogStorager` | `NewOperationLogStorager` | `ioperlog.OperationLogStorager` | `BatchCreate`、`List` |

`OperationLogStorager` 负责：
- 将 `OperationLogEntry` 批量转换为 `dao.TOperationLogParam` 后调用 `dao.TOperationLogCreate`；
- 查询时先 `dao.TOperationLogCount` 取总数，再 `dao.TOperationLogList` 分页读取；
- `change_summary` 在写入前由模型层完成 JSON 序列化，读取时反序列化回 `map[string]interface{}`。

#### 3.3.12 epp_pool 域

实现文件位于 `storage/rdb/epp_pool/`，对应接口定义在 `model/epp_pool`。

| 文件 | Storage 结构 | 构造函数 | 实现接口 | 主要方法 |
|------|--------------|----------|----------|----------|
| `epp_instance.go` | `RDBEppInstanceStorager` | `NewRDBEppInstanceStorager` | `epp_pool.EppInstanceStorager` | 实例池读写：按组查询/全量替换写入 `epp_instances`（`id` 池内全局唯一、`(host, port)` 联合唯一） |
| `epp_assignment.go` | `RDBEppAssignmentStorager` | `NewRDBEppAssignmentStorager` | `epp_pool.EppAssignmentStorager` | 分配读写：`epp_assignments` 按 `cluster` 唯一键 upsert/删除/查询（只存主，`primary_instance_id` 引用池内实例） |

`epp_instances` 一行一个实例，`group_name` 标识所属实例组；`epp_assignments` 一行一条 cluster 分配（`cluster` 唯一键），standby 不存储、由模型层读时展开为同组除 primary 外的实例。实例池写入为**全量替换**语义（对齐 `/alb-pool`），由模型层在事务内完成删除重建。

### 3.4 特殊 Storage 实现

#### 3.4.1 RouteRules 列表分页

`storage/rdb/route_rules/route_rules.go` 中的 `FetchRouteRulesList` 未使用 SQL `LIMIT`，而是在应用层做内存分页：

1. 先查询全部满足条件的记录（无分页）。
2. 计算总数 `total`。
3. 根据 `Page` / `PageSize` 计算偏移量，再次查询时加上 `Limit`。
4. 返回结果只包含 `type`、`owner`、`enabled`，不返回 `rules` 字段。

默认分页：`page = 1`，`pageSize = 20`，最大 `pageSize = 100`。

#### 3.4.2 产品级路由规则全量替换

`storage/rdb/route_conf/route_rule.go` 中的 `UpsertProductRule`：

1. 对 `route_advance_rules` 使用 `SELECT ... FOR UPDATE` 加锁。
2. 删除该产品线下的所有 `route_advance_rules` 和 `route_basic_rules`。
3. 批量插入新的规则。

#### 3.4.3 集群与子集群协同

`storage/rdb/cluster_conf/cluster.go`：

- 创建/更新/删除集群时，同时处理 `clusters`、`sub_clusters`、`lb_matrices` 三张表。
- `LLMConfig` 以 JSON 字符串存储在 `clusters` 表；多 API-Key 改造后，`llm_config` 中新增 `keys` 数组与 `key_policy` 对象，旧单 `key` 字段不再使用，但数据库表结构保持不变。
- `lb_matrices` 的 `lb_matrix` 字段以 JSON 字符串存储。

#### 3.4.4 AI 路由规则全量替换

`storage/rdb/ai_route/ai_route.go` 中的 `CreateAIRouteRules`：

1. 先删除 `ai_route_rules` 全表数据。
2. 再批量插入新的规则，并自动生成 `IDX`。

#### 3.4.5 配置版本控制

`storage/rdb/version_control/version_control.go` 中的 `UpsertConfigLastExportedVersion`：

- 按 `ORDER BY version DESC, id DESC` 读取该主题最新记录的 `data_sign` 并比较。
- 若签名相同则不插入，直接返回既有版本；若签名不同则新增一条记录。
- 候选版本取 `max(当前秒, 最新版本 + 1s)`，保证同 Topic 内版本号严格单调递增（同秒连续变更、时钟回拨均不会重复或倒退，issue #142）。
- 插入命中 `uk_name_version` 唯一约束（并发导出交错）时，重读最新行、版本 +1s 重试，上限 3 次，不整单报错。

### 3.5 存储层变更说明

#### 3.5.1 Cluster 对外模型与存储模型解耦

管理面 Cluster 接口对外隐藏 `ready`、`sub_clusters`、`scheduler`、`instance_pool` 等内部概念，但数据面导出仍依赖这些底层数据。Provider 与 Cluster 分离后，`instance_pool` 下沉到 `providers` 表，Cluster 创建/更新时由模型层读取 Provider 的 `instance_pool` 并同步生成 `pools`/`sub_clusters`。存储层表结构变化：

- 新增 `providers` 表，存储 Provider 接入能力（`model_endpoint`、`models`、`keys`、`instance_pool`、`model_protocols`）。
- `clusters` 表结构不变，`llm_config` JSON 中移除 `model_endpoint`、`provider_type`，`keys` 改为 `{name, weight}` 引用，`provider` 改为必填且须引用 `providers.name`。
- `pools` 表继续保存实例池数据，但数据源头由 Cluster 顶层下沉为 Provider `instance_pool`；映射与过滤由接口层/模型层完成。
- 对外模型：`basic`、`sticky_sessions`、`passive_health_check`、`llm_config`。
- 存储模型：`clusters` 表字段、`sub_clusters` 表、`pools` 表、`lb_matrices` 表、`providers` 表。

#### 3.5.2 API-Key 全局唯一性索引建议

支持创建 API-Key 时传入外部 `key`，要求全局唯一。当前 `api_key_tokens` 表已有唯一索引 `idx_key`，建议为 `api_keys.api_key` 字段也补充唯一索引：

```sql
ALTER TABLE api_keys ADD UNIQUE KEY uk_api_key (api_key);
```

#### 3.5.3 数据库表结构变更说明

Provider 与 Cluster 概念分离及模型定价改造引入了以下 schema 变更：

- 新增 `providers` 表，存储 Provider 接入能力；
- 新增 `model_prices` 表；
- `quota_plans.quota` 由 `BIGINT` 调整为 `DECIMAL(18,8)`；
- `quota_plans` 新增 `last_reset_at` 字段（由 `quota_balances` 表迁移而来）；
- 删除 `quota_balances` 表；
- `clusters` 表结构不变，`llm_config` JSON 中 `provider` 改为必填引用，`model_endpoint` 与 `provider_type` 移除，`keys` 改为 `{name, weight}` 引用结构，由接口层映射与参数校验实现；
- `pools` 表结构不变，实例池数据源头由 Cluster 顶层下沉为 Provider `instance_pool`。

例如 Cluster 多 API-Key 支持：将 `llm_config` 中的单 `key` 字段扩展为 `keys` 数组与 `key_policy` 对象；Provider 分离后，`keys` 元素进一步改为 `{name, weight}` 引用结构，但 `clusters` 表结构（含 `llm_config` text 字段）完全不变，仅修改接口层映射、模型层结构与校验规则。

## 5. 事务与上下文

### 5.1 事务抽象

模型层不直接依赖数据库事务，而是通过 `model/itxn.TxnStorager`：

```go
type TxnStorager interface {
    AtomExecute(ctx context.Context, f func(context.Context) error) error
}
```

`storage/rdb/txn/txn.go` 提供基于 `lib.DBContextFactory` 的实现：`RDBTxnStorager.AtomExecute` 会在同一个事务上下文中执行传入的函数。

### 5.2 DBContextFactory

所有 Storage 实现通过 `lib.DBContextFactory` 获取 `lib.DBContexter`：

```go
type DBContextFactory func(ctx context.Context) (DBContexter, error)
```

当调用链已处于事务中时，返回的 `DBContexter` 会复用同一个事务；否则使用普通连接。

### 5.3 跨表操作的事务边界

跨表操作通常由**模型层 Manager** 在 `AtomExecute` 回调内编排，例如：

- `EntityManager.CreateEntity`：在一个事务中依次创建 QuotaPlan、RateLimitPolicy、RouteRules、Entity。
- `APIKeyManager.DeleteAPIKey`：在一个事务中依次删除 QuotaPlan、RateLimitPolicy、RouteRules、API-Key。
- `RouteRuleStorager.UpsertProductRule`：在一个事务中删除并重建产品的路由规则。

Storage 层本身一般不开启事务，仅负责单表或同域内几张表的读写转换。
