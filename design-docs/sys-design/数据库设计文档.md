# Rainway AI Gateway - 数据库设计文档

## 1. 概述

本文档描述 `ai-gateway-api` 当前代码实现中使用的数据库表结构，覆盖基础配置、集群与实例池、路由规则、证书与附加文件、API Key / Entity / 配额 / 限流等全部持久化表。

### 1.1 数据库引擎与访问方式

| 项目 | 说明 |
|------|------|
| 底层驱动 | 标准库 `database/sql` |
| SQL 构建器 | `github.com/didi/gendry`（builder + scanner） |
| 支持数据库 | MySQL 5.7+、SQLite |
| 连接管理 | `stateful/config_database.go`：`NewDB()` / `BFEDB()` |
| 事务封装 | `lib/xdb.go`：`DBContext` / `Transaction` |
| ORM 风格 | 无 ORM，通过 `db` tag 将 Go struct 映射到表字段 |

### 1.2 通用约定

- 所有表均包含 `created_at` 与 `updated_at` 字段。
- MySQL 中 `updated_at` 默认使用 `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`；SQLite 通过 trigger 模拟该行为。
- 数据库 DDL **未声明物理 FOREIGN KEY 外键约束**，表间关系均为逻辑外键，由应用层代码维护。
- 历史表主要使用 `utf8` 字符集；AI 相关表（`api_keys`、`entity_types`、`entities`、`quota_plans`、`rate_limit_policies`、`route_rules` 等）使用 `utf8mb4`。

### 1.3 表清单

按业务模块划分，共 29 张表：

| 模块 | 表名 |
|------|------|
| 基础配置 | `bfe_clusters`、`products`、`domains`、`users`、`user_products`、`config_versions` |
| Provider | `providers` |
| 集群与实例池 | `clusters`、`sub_clusters`、`pools`、`lb_matrices` |
| 路由规则 | `route_basic_rules`、`route_advance_rules`、`route_default_rules`、`route_cases`、`ai_route_rules`、`route_rules` |
| 证书与附加文件 | `certificates`、`extra_files` |
| API Key / Entity / 配额 / 限流 | `api_keys`、`api_key_id_seq`、`api_key_tokens`、`entity_types`、`entities`、`entity_id_seq`、`quota_plans`、`rate_limit_policies` |
| 模型定价 | `model_prices` |
| 操作日志 | `operation_logs` |

## 3. Provider 与集群实例池表

### 3.1 `providers`

Provider 配置表，集中管理下游模型提供方的接入能力。

```sql
CREATE TABLE `providers` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT,
  `name` varchar(255) NOT NULL,
  `description` varchar(1024) NOT NULL DEFAULT 'no desc',
  `model_endpoint` text,
  `models` text,
  `keys` text,
  `instance_pool` text,
  `model_protocols` text,
  `time_zone` varchar(255) NOT NULL DEFAULT 'Asia/Shanghai',
  `tiers` text,
  `created_at` datetime NOT NULL,
  `updated_at` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `name_index` (`name`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | bigint(20) | 主键、自增 | 主键 ID |
| `name` | varchar(255) | NOT NULL、唯一 | Provider 唯一标识；合法命名参考 `ClusterName` |
| `description` | varchar(1024) | NOT NULL DEFAULT 'no desc' | 描述 |
| `model_endpoint` | text | NULL | 模型发现端点 JSON，默认 `{schema: "https", uri: "/v1/models"}` |
| `models` | text | NULL | 支持的模型列表 JSON |
| `keys` | text | NULL | API Key 明文列表 JSON；元素为 `{name, key}` |
| `instance_pool` | text | NULL | 后端实例池 JSON；元素为 `{name, addr, weight, port}` |
| `model_protocols` | text | NULL | 支持的模型访问协议 JSON；首期枚举：`openai`、`anthropic` |
| `time_zone` | varchar(255) | NOT NULL DEFAULT 'Asia/Shanghai' | 计算时段所使用的时区；IANA 时区名 |
| `tiers` | text | NULL | 时段 tier 定义列表 JSON；元素为 `{name, time_ranges}`；**初期 `name` 只支持 `peak`** |
| `created_at` | datetime | NOT NULL | 创建时间 |
| `updated_at` | timestamp | 自动更新 | 更新时间 |

> 说明：`time_zone` / `tiers` 描述该 provider 的时段规则，供 InnerAPI 导出 `AIConf.ModelTable` 时使用。同一 provider 下所有模型共享该规则。

> 说明：`providers` 表使用 `utf8mb4` 字符集以支持模型名等多语言内容。Provider 被 `/clusters` 引用时不可删除；`/model-prices` 中的同名 provider 不再阻塞删除。

### 6.7 `api_key_id_seq`

API-Key ID 序号分配表，用于原子分配 `api-key-{seq}` 形式的业务 ID（修复并发创建 ID 竞态，见 modifications/2026-08-23-issue-80-apikey-id-race 与 2026-08-27-issue-99-apikey-id-lock-wait-timeout）。

```sql
CREATE TABLE `api_key_id_seq` (
  `product_name` varchar(255) NOT NULL COMMENT '产品线名称',
  `next_seq` bigint NOT NULL DEFAULT '1' COMMENT '下一个可用序号',
  PRIMARY KEY (`product_name`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='API-Key ID序号分配表';
```

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `product_name` | VARCHAR(255) | 主键 | 产品线名称；按产品线独立分配序号 |
| `next_seq` | BIGINT | NOT NULL DEFAULT 1 | 下一个可用序号；分配即消耗，删除 API-Key 后不回退 |

**分配语义**：`next_seq` 表示下一个可用序号。MySQL 通过单条 `INSERT ... ON DUPLICATE KEY UPDATE` + `LAST_INSERT_ID()` 原子自增并读回；SQLite 通过 `INSERT OR IGNORE` + `UPDATE` + 读回。已分配序号永久消耗，即使后续创建失败或事务回滚也不会复用。

> 说明：`api_key_id_seq` 与业务表无外键关系；`next_seq` 必须初始化为当前最大 `api-key-N` 序号 + 1（升级脚本见对应 modifications 文档）。

### 6.8 `entity_id_seq`

Entity ID 序号分配表，用于原子分配 `entity-{seq}` 形式的业务 ID（修复并发创建 ID 竞态与删除后 ID 复用问题，见 modifications/2026-09-04-issue-132-entity-id-race）。

```sql
CREATE TABLE `entity_id_seq` (
  `name` varchar(32) NOT NULL COMMENT '序号键（固定为entity）',
  `next_seq` bigint NOT NULL DEFAULT '1' COMMENT '下一个可用序号',
  PRIMARY KEY (`name`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Entity ID序号分配表';
```

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `name` | VARCHAR(32) | 主键 | 序号键；Entity 序号全局唯一，固定为 `entity`。预留主键以便表结构复用 |
| `next_seq` | BIGINT | NOT NULL DEFAULT 1 | 下一个可用序号；分配即消耗，删除 Entity 后不回退，保证旧 ID 永不复用 |

**分配语义**：与 `api_key_id_seq` 相同（MySQL 单语句原子自增 / SQLite `INSERT OR IGNORE` + `UPDATE` 读回），由 `EntityIDGenerator`（`model/entity/id_generator.go` 接口，`storage/rdb/entity/id_generator.go` 实现）在 Entity 创建时调用，生成的 ID 格式为 `entity-{seq}`。

> 说明：`entity_id_seq` 与业务表无外键关系；`next_seq` 必须初始化为当前最大 `entity-N` 序号 + 1（升级脚本见对应 modifications 文档）。

## 9. 备注

1. **无物理外键**：所有表关系靠业务代码维护，删除时需注意级联清理（例如 `DeleteAPIKey` 会同步删除关联的 quota、rate_limit、route_rules 等）。
2. **`users` 表复用**：普通用户与 API Token 共用 `users` 表，通过 `type` 字段区分：0=普通用户，1=Token。
3. **`route_cases` 表**：仅在 DDL 中定义，当前代码中无对应 DAO 与业务代码引用。
4. **MySQL 与 SQLite**：字段类型等价；SQLite 通过 trigger 模拟 `updated_at` 自动更新。
5. **JSON 字段**：`providers.model_endpoint`、`providers.models`、`providers.keys`、`providers.instance_pool`、`providers.model_protocols`、`providers.tiers`、`instance_detail`、`lb_matrix`、`llm_config`、`allowed_models`、`subnet`、`tpm_configs`、`rpm_configs`、`rules`、`basic`、`params`、`route_action`、`host_names`、`paths`、`model_prices.capabilities`、`model_prices.supported_parameters`、`model_prices.limits`、`model_prices.prices`、`model_prices.tier_prices`、`model_prices.metadata` 等字段均为 JSON 或文本序列化存储。
